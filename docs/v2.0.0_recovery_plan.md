# Version 2.0.0 Recovery Plan

## Purpose

This plan restores the original portfolio scope of the Dental Appointment No-show Prediction project after the premature `v1.0.0` release.

The current `v1.0.0` release is retained as an auditable methodological checkpoint. Recovery work must occur on:

```text
recovery/v2.0.0-completion
```

No recovery work should be committed directly to `main`.

## Confirmed audit baseline

The state below records the post-`v1.0.0` audit baseline. It is retained for
historical context and is not a description of the current recovery branch.

The following directories contained only placeholders and no meaningful implementation at that checkpoint:

- `app/`
- `models/`
- `notebooks/`
- `data/interim/`
- `data/processed/`
- `reports/figures/`
- `reports/screenshots/`
- `src/features/`
- `src/evaluation/`
- `src/models/`

The repository did contain substantial implementation under:

- `src/data/`
- `src/analysis/`
- `src/modeling/`
- `tests/`
- `docs/`
- `.github/workflows/`

No tracked Python cache or bytecode files were found in the current Git index.

## Recovery principles

1. Preserve the original `v1.0.0` tag and release as an audit checkpoint.
2. Do not reuse the previously observed test period for new model selection.
3. Do not build a patient-level risk calculator unless the recovered model demonstrates useful appointment-level ranking.
4. Keep all feature construction prediction-time safe and reproducible.
5. Add user-facing outputs only after the evaluation design is frozen.
6. Require documented acceptance criteria before each recovery phase is merged.
7. Release `v2.0.0` only after the original charter deliverables are complete.

## Phase R1 — Leakage-safe historical features and renewed evaluation policy

**Status: complete on the recovery branch.**

`44765dd`; the full local suite reported `1534 passed`, GitHub CI was green, and

### Goals

Create reproducible as-of historical features that may contain real predictive
signal while preserving the 24-hour prediction-time contract.

### Implemented historical features

The frozen feature contract defines 32 approved predictors consisting of:

- 11 prediction-time-safe current appointment features;
- 12 strict-as-of patient-history features; and
- 9 strict-as-of dentist, visit-type, and weekday-hour aggregate-history
  features.

Every historical feature uses only records satisfying:

```text
historical_status_updated_at < current_prediction_time
```

The attendance-rate denominator contains only `completed` and `no_show`
appointments. No-show rates use the predeclared Beta `(1, 9)` prior, and
aggregate rates require 10 prior attendance opportunities before emitting a
supported group rate.

### Evaluation policy

The previously examined Version 1 test period remains an audit checkpoint and
is not reused for recovery model selection.

Version 2 uses the separately generated longitudinal benchmark and the
chronological schedule frozen in
`docs/v2_data_generation_and_evaluation_policy.md`, including the protected
future test window:

```text
2027-01-01 <= prediction_time < 2028-01-01
```

The committed processed feature artifact is target-free. Final-test target
access is a separate gated operation that requires an explicit opt-in and a
complete probability vector written and SHA-256 sealed before target loading.

### Goals

Re-run the project using the new leakage-safe feature set and renewed evaluation policy.

### Required models

- population-prior baseline
- Logistic Regression

- optional additional model only when methodologically justified

### Required evaluation

- Average Precision / PR-AUC
- ROC-AUC
- Brier score

### Threshold policy

Document false-positive and false-negative assumptions, break-even behavior, and sensitivity analysis. Do not default to `0.50`.

### App decision gate

At the end of this phase, choose one app type:

#### Option A — Appointment-level risk demonstration

Allowed only if the final model demonstrates useful ranking and probability behavior beyond the prior baseline.

#### Option B — Transparent model-evaluation dashboard

Required if individualized prediction remains unsupported. The app should explain the negative result, calibration, threshold economics, and limitations without presenting misleading individual risk.

- model artifacts can be loaded successfully
- error and subgroup analyses are documented
