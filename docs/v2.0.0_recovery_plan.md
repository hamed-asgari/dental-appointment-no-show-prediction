# Version 2.0.0 Recovery Plan

## Purpose

This plan restores the original portfolio scope of the Dental Appointment No-show Prediction project after the premature `v1.0.0` release.

The current `v1.0.0` release is retained as an auditable methodological checkpoint. Recovery work must occur on:

```text
recovery/v2.0.0-completion
```

No recovery work should be committed directly to `main`.

## Confirmed current state

The following directories contain only placeholders and no meaningful implementation:

- `app/`
- `models/`
- `notebooks/`
- `data/interim/`
- `data/processed/`
- `reports/figures/`
- `reports/screenshots/`
- `src/features/`
- `src/evaluation/`
- `src/models/`

The repository does contain substantial implementation under:

- `src/data/`
- `src/analysis/`
- `src/modeling/`
- `tests/`
- `docs/`
- `.github/workflows/`

No tracked Python cache or bytecode files were found in the current Git index.

## Recovery principles

1. Preserve the original `v1.0.0` tag and release as an audit checkpoint.
2. Do not reuse the previously observed test period for new model selection.
3. Do not build a patient-level risk calculator unless the recovered model demonstrates useful appointment-level ranking.
4. Keep all feature construction prediction-time safe and reproducible.
5. Add user-facing outputs only after the evaluation design is frozen.
6. Require documented acceptance criteria before each recovery phase is merged.
7. Release `v2.0.0` only after the original charter deliverables are complete.

## Phase R1 — Leakage-safe historical features and renewed evaluation policy

### Goals

Create reproducible as-of historical features that may contain real predictive signal while preserving the 24-hour prediction-time contract.

### Candidate historical features

- prior eligible appointment count
- prior no-show count
- prior no-show rate
- prior cancellation count
- days since previous appointment
- previous appointment outcome
- patient tenure
- dentist historical no-show rate
- appointment-type historical no-show rate
- booking lead-time history where available

Every feature must use only records strictly available before the prediction timestamp.

### Evaluation-policy requirement

The previously examined test period is no longer untouched.

Before training recovered models, define one of these policies:

1. a newly generated prospective synthetic extension with a frozen future test period; or
2. a redesigned rolling-origin evaluation with a final future window that is not used for selection.

The selected policy must be documented before any recovered model is evaluated.

### Deliverables

- historical-feature specification
- reusable feature builder under `src/features/`
- leakage tests
- updated data dictionary
- updated processed-data manifest
- renewed temporal evaluation policy

### Acceptance criteria

- no row can use future appointment outcomes
- feature calculations are deterministic
- leakage tests pass
- new evaluation periods are frozen before modeling

## Phase R2 — Recovered modeling, calibration, and threshold analysis

### Goals

Re-run the project using the new leakage-safe feature set and renewed evaluation policy.

### Required models

- population-prior baseline
- Logistic Regression
- at least one deterministic tree-based model
- optional additional model only when methodologically justified

### Required evaluation

- Average Precision / PR-AUC
- ROC-AUC
- Brier score
- log loss
- precision and recall at documented thresholds
- confusion matrices
- calibration curves
- chronological validation results
- comparison against the population-prior baseline

### Calibration

Compare uncalibrated probabilities with sigmoid and isotonic calibration only on appropriate chronological calibration data.

### Threshold policy

Document false-positive and false-negative assumptions, break-even behavior, and sensitivity analysis. Do not default to `0.50`.

### Acceptance criteria

- model ranking and calibration are reported separately
- the final candidate is chosen without consulting the new frozen test labels
- results are reproducible from one command
- all claims remain proportional to synthetic-data evidence

## Phase R3 — Interpretation, error analysis, persistence, and reproducibility

### Goals

Make the modeling workflow inspectable and reusable.

### Deliverables

- reproducible modeling runner
- persisted preprocessing/model artifact when appropriate
- machine-readable metadata
- model card
- feature-importance or permutation-importance analysis
- error analysis
- first-time versus repeat-patient diagnostics
- subgroup diagnostics where sample sizes support them
- final chronological test evaluation
- committed summary tables and key figures

### App decision gate

At the end of this phase, choose one app type:

#### Option A — Appointment-level risk demonstration

Allowed only if the final model demonstrates useful ranking and probability behavior beyond the prior baseline.

#### Option B — Transparent model-evaluation dashboard

Required if individualized prediction remains unsupported. The app should explain the negative result, calibration, threshold economics, and limitations without presenting misleading individual risk.

### Acceptance criteria

- one documented command reproduces the final analytical outputs
- model artifacts can be loaded successfully
- error and subgroup analyses are documented
- app type is chosen using explicit evidence
